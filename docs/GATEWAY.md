# 网关能力审计与分析

本文回答一个问题：**服务治理的全部工作，能不能放进 goacos？**

结论先行：**能，而且已经做完了。** goacos 现在既是注册中心（Nacos 兼容），也是总网关
（Go 原生数据面），一个二进制同时承担 API 分发与网页分发。剩下的不是"能不能"，
而是"哪些治理能力**不应该**内置"——这一节同样重要，因为它决定了 goacos 的边界在哪里。

本文既是审计结论，也是架构决策记录。每一条"已实现"都对应可运行的代码与测试，
而不是设想。

---

## 一、审计结论：先看现状缺什么

审计从代码和部署现状出发，而不是从设想出发。三个事实决定了方案。

### 事实一：命名模型表达不了"一个完整应用"

Nacos 的注册模型是 `namespace → group → service → instance`。它能回答
"服务 X 现在有哪些健康实例"，但回答不了"acc-api.itestu.cn 该去哪"——因为后者涉及
**域名**、**应用边界**和**组件角色**（前端 / 后端 / worker），这三样都不在 Nacos 的词汇表里。

结果是每一台网关都得自己维护一张手写的 `domain → host:port` 表。这不是假设，是已经
发生过的事：平台里两张这样的表已经在生产上漂移不一致。

**修复方式不是"再维护好一张表"，而是让注册中心本身能承载这份策略。**

### 事实二：路由策略与实例状态必须来自同一个真相源

只要路由表里写了 IP 和端口，就立刻有了第二份真相源。实例注册表会变（心跳、摘除、
扩缩容），手写表不会——两份数据必然漂移，而漂移的方向总是"流量打到一个已经下线的实例"。

所以本项目的应用模型里**刻意没有任何 ip / port 列**。组件只声明"我是哪个服务的哪个角色"，
实例在解析时从 `naming_instance` 实时读取。这条约束有测试守着
（`TestApplicationModelHasNoAddressColumns`），谁想加回地址列，CI 会拦。

### 事实三：nginx 能做的不只是转发

一旦决定"把网关放进 goacos"，就必须回答：**nginx 那些能力，哪些是必须有的？**
只做反向代理是不够的，因为审计看到的前端诉求里明确包含"证书"和"流量处理"。

## 二、能不能把服务治理全部放进本项目：可以，已实现

下面每一项都已落地并通过测试。括号内是证据位置。

### 2.1 应用模型：把"应用"变成一等公民

```
application ──┬── application_component ──→ naming service → instances
              └── route_binding (domain + path prefix) ──────→ component
```

| 能力 | 位置 |
|---|---|
| 应用 / 组件 / 路由声明、查询、级联删除 | `internal/storage/appstore.go`、`internal/api/app_v1.go` |
| 一次查询拿到「策略 + 实时健康实例」 | `ResolveRoute()`、`GET /goacos/v1/route/resolve` |
| 模式演进 | 迁移 002，双引擎 |

关键设计：**最长前缀优先**，所以 `acc.itestu.cn/ui/*` 可以路由到前端，
`/api/*` 路由到后端，而同一个域名还能有 `/` 兜底。前缀匹配强制段边界，
`/api` 不会误伤 `/apixyz`。

### 2.2 网关数据面：真的在收发流量

| 能力 | 位置 | 说明 |
|---|---|---|
| Host + 路径路由 | `internal/gateway/routetable.go` | 定时重建的内存快照，请求路径零查询 |
| 反向代理 | `proxy.go` | 完整 URL 转发、X-Forwarded-* 重建、上游看到真实 Host |
| 负载均衡 | `lb.go` | nginx 同款平滑加权轮询 + least_conn + ip_hash + cookie_sticky |
| 故障转移 | `proxy.go` | 仅在**尚未写出响应**时重试，等价于 `proxy_next_upstream` |
| 权重 / 元数据路由 | `appstore.go` | `metaFilter=lane=canary` 灰度，无需改实例表 |
| WebSocket | `policy.go` / `proxy.go` | 可按域开关，长连接不被响应头超时切断 |
| 静态网页 + SPA | `static.go` | 本地目录交付、SPA index.html 回退、指纹资源不可变缓存 |
| 优雅停机 | `gateway.go` | 连接池释放、监听器 shutdown |

### 2.3 证书：这是"自动带上 nginx 功能"里最难的一块

已实现的三层机制：

1. **ACME 自动签发为默认路径**（`acme.go`）。RFC 8555 + HTTP-01 验证，走
   `golang.org/x/crypto/acme`，无新增依赖。
2. **自签证书兜底**（`selfsigned.go`）。**任何已声明的域名，永远能完成 TLS 握手**——
   握手失败在运维视角等于"网站挂了"，但真实故障（证书还没签下来）在这个层面完全不可见。
3. **手动上传**（`POST /goacos/v1/certs`）。内部 CA / 气隙环境的出口，且**永不自动续期**，
   因为没有任何人比运维更清楚该换成什么。
4. **共享目录**（`GOACOS_GATEWAY_CERT_DIR`）。证书已经由 certbot / cert-manager /
   内部 PKI 工具在宿主机上管好时，挂载进来即可直接对外服务，不必手工复制进数据库；
   同时 goacos 签发的证书会原子回写到同一目录供其他组件复用。

   目录**不在握手路径上被读取**——按定时器扫描、解析一次、与数据库来源共用同一份内存缓存。
   否则宿主机繁忙或挂载卷变慢会直接表现成握手失败风暴。

   优先级规则是这套设计的关键：**外部 CA 签发的证书压过自签占位证书**。
   否则会出现典型的坑——域名先声明、goacos 补了自签并尝试 ACME，之后运维才挂载上
   certbot 早就签好的证书，结果该域名永远在服务自签证书，而有效证书躺在磁盘上没人读。
   目录里若本身是自签的，会被识别为占位证书，不参与压制真实证书。

SNI 多证书、到期前 21 天自动续期、HSTS、HTTP→HTTPS 跳转、`Strict-Transport-Security`
全部具备。响应头带 `X-Goacos-Cert-Source`，运维不必打开浏览器就能看出"这个域名还跑在自签证书上"。

### 2.4 流量治理：按域策略

`gateway_vhost` 表提供每域策略：强制 HTTPS、HSTS、IP 黑白名单、请求体上限、
连接/读写超时、WebSocket 开关。未声明的域名继承全局默认。

## 三、关键设计决策与理由

审计的价值一半在"做了什么"，另一半在"为什么这么做"。以下几条是踩过坑之后的结论。

### 3.1 为什么路由表是定时快照，而不是每次查询

`ResolveRoute` 是正确的、也是唯一真相源，但它是一次多表 join。**把它放到每一条入站流量的
路径上，等于把数据库变成全站流量的单点**——这正是"注册中心拖垮业务"的经典死法。

所以数据面持有一份内存快照，按固定间隔重建。代价是一个**明确且有界**的陈旧窗口
（默认 10 秒，`GOACOS_GATEWAY_REFRESH_SECONDS`），换来的是请求路径上的成本降到几次 map 查找。

刷新失败时**保留上一份快照**：空快照和"所有路由都被删了"在行为上无法区分，
一次数据库抖动不该让全站下线。

### 3.2 为什么故障转移必须在写响应之前决定

客户端已经收到 500 的第一个字节之后再换个实例重放，会产生"一个请求两个应答"，
在支付这类场景下会直接重复扣款。所以代理层**只记录错误不写响应**，由上层在确认
"还没写过任何东西"时才决定是否换实例。

### 3.3 为什么内部上游默认走明文

审计中一个容易做错的地方：客户端走 HTTPS进来，就顺手让网关跟上游也用 TLS。
这是错的——网关的职责就是在边缘终结 TLS，再以合适的协议回源。
除非组件显式声明 `protocol: https`，否则一律明文拨号，
这样内网 8080 端口的服务不需要为了"给网关看"而单独申请一张证书。

### 3.4 为什么 ACME 有资格预检

公共 CA 的失败配额是硬约束（Let's Encrypt：每账号每小时 5 次失败授权）。
一个对所有已声明域名盲目尝试签发的网关，会把配额消耗在 `api.internal`、`localhost`、
`10.0.0.7` 这些永远签不下来的名字上，然后**真正需要证书的公网域名反而签不出来**。

所以发往 CA 之前先过两道闸：名字是否可能被公共 CA 服务（非内网后缀、非 IP、非通配符），
以及当前是否解析到公网地址。失败后退避 5min → 10min → … → 6h，**结构性签不下来的域名
不会持续消耗共享的配额**。

### 3.5 为什么静态资源路径沿用 nginx 语义

`protocol=static` 的组件，请求路径在组件根目录下**完整解析**（与 nginx `root` 一致），
而不是相对于路由前缀剥离。这条规则让同一份构建产物可以被多个域名复用，也让"这个文件
到底在哪"这个问题有唯一答案。

反过来讲，对于代理型组件，默认**保留完整路径**，剥离前缀必须通过组件元数据
`stripPrefix=true` 显式开启。前后端路径约定不一致时，静默猜测约定会打挂一个本来健康的应用——
所以宁可多写一个配置项。

### 3.6 决定「前端还是后端」的是 protocol，不是 kind

一个组件同时有 `kind` 与 `protocol` 两个字段，只有后者决定**交付方式**：

| 字段 | 取值 | 作用 |
|---|---|---|
| `kind` | `web` / `api` / `worker` / `mcp` / `gateway` | **描述性**。存下来、在 API 里返回；不决定交付方式，但未声明 `lbAlgorithm` 时它决定默认算法（`web` → `ip_hash`） |
| `protocol` | `http` / `https` / `static` / `grpc` / `ws` | **决定性**。只有 `static` 会走磁盘交付，其余一律代理 |
| `metadata.delivery` | `static` / `proxy` | 显式覆盖 `protocol`，无需改写路由 |

判定链在 `internal/gateway/static.go`：

1. `protocol != static` → `staticRoot()` 直接返回空 → 一定代理。**这一步先于任何
   磁盘检查**，所以 API 组件不可能被误当成静态站点；
2. `protocol == static` → 取 `<静态根>/<app>-<component>`，目录存在则从磁盘交付，
   不存在则退回代理；
3. `metadata.delivery` 为 `proxy` 或 `static` 时，跳过第 2 步的目录判断，直接指定。

**所以 `kind: web` + `protocol: http` 表示「前端，但它由上游代理交付」**，不是
「前端，由 goacos 从磁盘交付」。这两种部署在 itestu 上都存在：openpocket / smm /
portal 三个组件走 `protocol=static`，其余 web 组件走 `http`（前端由 nginx 交付，
goacos 只做数据面）。

**`protocol=static` 的组件不需要 `serviceName`**，因为它的交付路径根本不查命名服务：
静态根目录只按 `app` + `component` 取，`ServeStatic` 直接从磁盘答。曾经统一要求
`serviceName`，是契约缺陷而不是安全栏 —— 它逼着静态前端编一个占位服务名，而这个占位名
**并不证明**建出了对应的 `naming_service` 记录。其余协议（`http` / `https` / `grpc` /
`ws`）仍必须填，且检查**失败关闭**：不是精确的 `static`（含 `stattic` 这类拼写错误）
一律按实例型处理。

写 `kind: web` 的人通常以为它决定了交付方式。它不会 —— 决定的是 `protocol`。

### 3.7 台账里的 `!` 兜底，在数据面上必须真的兜底

台账 `service-map.conf` 用 `!` 前缀表达「这一行是兜底」，reconcile 据此给实例写
`metadata.role=backup`（`goacos-reconcile.sh:176`）。nginx 的 `backup` 语义是
「平时不参与轮转，本组全挂才顶上」。

网关的负载均衡选择**只看 `clusterName` 与 `enabled`，完全不看 `role`**，而 primary 与
backup 注册时 `weight` 又都是 1.0 —— 两者排序完全平权。于是台账里那几行带兜底的记录
会**各拿到约一半流量**。更糟的是那些兜底行指向 loopback：注册中心侧它们还显示
healthy，是最难排查的那一类错误。

修法把两个视图分开：

| 视图 | 函数 | 兜底实例 |
|---|---|---|
| **数据面**（真正转发） | `selectForwardable` | 有 primary 时**不进入**转发集合；全是 backup 时**照常转发** |
| **运维面**（`/goacos/v1/routes`、传输池） | `selectInstances` | **始终可见** |

数据面之所以「全是 backup 时照常转发」，是刻意的**失败开放**：一个被打错标签的服务
整体不答应，比用兜底顶上坏得多 —— nginx 行为相同（全是 backup 的组照样应答）。
没有 `role` 标注的实例按普通实例处理，因为 `!` 语法出现之前注册的实例都是这样，
把「未知」当成「备用」会让它们集体消失。

运维面**不能**跟着过滤：出问题时运维界面上必须看得到 backup，隐藏它等于让
「这个服务为什么 502」这件事无从查起。同理，传输池的存活地址计算走的是未过滤的
视图 —— 兜底实例此刻虽然不转发，但它的连接池必须留着，否则真到该顶上时连接已被回收。

判据在 `internal/gateway/backup_role_test.go`，其中一条是**端到端**的：兜底节点
**活着并应答**，只是不该被选中 —— 因为「兜底不可达」测不出「兜底该不该被选中」，
不可达这件事本身已经被另一层故障转移兜住了。

## 四、哪些治理工作**不应该**放进本项目

这是审计最重要的产出。把所有东西都塞进一个二进制，看起来统一，实际上会造出新的耦合。

| 不该内置 | 理由 | 该在哪 |
|---|---|---|
| **限流 / 熔断** | 需要业务语义（哪些接口限多少、按用户还是按 IP），网关猜不出来；且强耦合会让网关成为扩容瓶颈 | 服务网格（Envoy / Istio）或业务侧 |
| **服务间 mTLS** | 网关只终结外部 TLS，东西向加密需要每服务一张证书与轮换策略 | Sidecar / 服务网格 |
| **灰度权重编排** | 网关已支持 `metaFilter` 选实例，但"何时把 5% 提到 20%"是发布决策 | 发布平台 |
| **大文件上传 / 视频点播** | 需要与对象存储、Range 请求、分片续传深度协同 | CDN |
| **WAF / SQL 注入检测** | 正则型检测的误报率和维护成本，远超其收益 | 独立的 WAF 产品或云服务 |
| **多集群 / 多区域流量调度** | 需要全局拓扑视角，单实例网关看不到 | 外部 DNS /GSLB |

**判断标准**：一项能力如果**做错了会导致全站故障**，且**正确实现需要业务知识**，
就不应该内置。网关应该只保留"做错最坏结果是这一个域名的流量分配变差"的能力。

## 五、已实现 vs 尚未覆盖

诚实起见，列清楚边界。

**已实现并验证**：应用模型、双引擎迁移、路由解析、Go 原生反向代理、四种负载均衡、
故障转移、WebSocket、静态前端与 SPA、ACME 自动签发与续期、自签兜底、SNI 多证书、
HTTP→HTTPS、HSTS、IP 黑白名单、请求体上限、每域超时、状态与证书管理 API、
优雅停机、双引擎（MySQL 8 / PostgreSQL 16）端到端验证。

**尚未覆盖**（有意为之，见上表）：限流、熔断、服务间 mTLS、WAF、CDN 集成、
多集群调度、通配符证书（HTTP-01 无法验证通配符，需要 DNS-01）。

## 六、运维要点

**一个域名的上线顺序**：声明 app → 声明 component → 注册实例 → 声明 route。
**证书不需要人工介入**：route 声明后，ACME 自动签发；签不下来时自签兜底保证不中断，
控制台与 `X-Goacos-Cert-Source` 明确标注"这是自签证书"。

**排障顺序**：`GET /goacos/v1/gateway/status` 一屏给出四件事——
路由快照年龄、每个域名的证书来源与剩余天数、ACME 退避状态、各组件的存活实例数。
证书来源为 `file` 的域名会附带 `tlsPath`，指回磁盘上的位置。

**Docker 权限**：镜像内以 uid 10001 运行，挂载目录必须对该 uid 可读
（开启回写时还需可写）。root 属主的 `0700` 目录会导致一张证书都加载不出来，
且没有任何明显提示——这是这个特性最常见的故障形态。
按这个顺序看，能覆盖绝大多数"网站打不开"的场景，不需要先 curl 一下再猜。

**升级前置**：网关默认关闭（`GOACOS_GATEWAY_ENABLED=false`），把 goacos 加进现有环境
不会突然开始抢 80/443 端口。确认配置无误后再打开。

**命名清扫的索引**：命名清扫每 `SWEEP_INTERVAL_MS`（默认 5s）跑三条按
`(ephemeral, healthy, last_heartbeat_ms)` 过滤 `naming_instance` 的语句，而库里原有的
索引全部以 `namespace_id` 打头，都用不上 —— 于是每 5 秒三次全表扫描，永久地。
迁移 004 补上 `idx_instance_sweep (ephemeral, healthy, last_heartbeat_ms)`，一次索引
覆盖三条语句，20,000 实例的实测：50 个清扫周期从约 1.4~1.8 秒降到 24~285 毫秒。
**只有一条索引**是有意的：心跳 UPDATE 是这个表的热路径，索引越多，每一跳的写放大越大。
